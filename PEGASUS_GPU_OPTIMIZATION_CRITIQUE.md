# PegaSUS Optimization + GPU-Acceleration Rematch

Objective 3: speed/memory/compute redesigns, and — critically — a FRESH assessment of GPU/CUDA/PyTorch acceleration for the heavy math (EFG, and especially the LDO), given the mathematical developments since the last (pessimistic) GPU assessment. Environment: torch 2.5.1, CUDA on RTX 4050 Laptop (6.4 GB VRAM), `compute.yaml dtype=float32, max_vram_fraction=0.80`. GPU currently wired ONLY for HSIC (pirs_hsic_*), race-bridge, STDFM — **nothing in the LDO estimator core**.

**Why the rematch is justified (the reframing):** the earlier assessment judged *single* operations — one `p≈130` eigh, one `S` solve — which are indeed trivial and CPU-fast. But the LDO's actual workload is now dominated by MANY REPEATED small-dense operations, and that count has GROWN with every math development since: stability selection (`n_subsamples` refits × ~500 ADMM iters), the O4 λ-grid path refits, the O3 exact-vs-approx slice refits, the O5 temporal-holdout refits, the multiresolution coarse+fine refits, and the O(p²) pairwise HSIC scan. GPUs win on exactly this — batched identical small kernels — not on one big op. The workload shape changed; the conclusion should be re-derived.

## Part A — Lead's direct GPU-rematch assessment

### G1 · `GPU-STAB-BATCH` — HIGH — batch the stability-selection ADMM refits on GPU (the ideal batch)
- **detail:** `stability_select` runs `n_subsamples` (12–20) INDEPENDENT CPW-ADMM fits, each ~500 iterations whose hot step is a `p·(K+1)` (≈130) symmetric eigh (`_prox_neg_logdet`, `_psd_project_shifted`). This is the textbook GPU batch: many identical small dense eigendecompositions. `torch.linalg.eigh` is batched — run all `n_subsamples` subproblems' eigh as one `(n_sub, p, p)` batched call per ADMM iteration. A batch of 20× 130×130 eigh is negligible VRAM (~20·130²·4 B ≈ 1.4 MB) and saturates the GPU. This parallelizes the LDO's dominant wall-clock without any accuracy change (eigh is exact).
- **value:** HIGH — the single biggest LDO speedup; also composes with A15 (redundant per-subsample whitening) once the whitening is precomputed once.
- **plan:** a `torch`-backed batched ADMM in a new `ldo/torch_admm.py` behind `resolve_torch_device("ldo_admm", prefer_cuda=True)` with a numpy fallback; the S/L/U/R iterates as `(n_sub,p,p)` GPU tensors; soft-threshold + batched eigh + PSD-clip all batched. Determinism via `seed_everything`. Validate vs the numpy ADMM within float32 tolerance.

### G2 · `GPU-HSIC-SCAN` — HIGH — the residual HSIC scan is CPU-only despite hsic.py having GPU paths; it is the largest LDO allocation
- **detail:** `residual_scan.py` reimplements the HSIC pairwise scan importing only the NUMPY private helpers (`_bandwidth`, `_np_nystrom_features`, `_np_rff_features`) — it never touches the GPU, even though `hsic.py` has CUDA-mode paths (now orphaned per O9). The scan builds a per-variable representation cache (dense `n_eff×n_eff` kernels or `n_eff×features` maps) and scores every O(p²) pair under a shared permutation set — the single largest national LDO allocation (~48 GB at exact `n_eff=5000`, per `estimate_residual_scan_bytes`). Kernel Gram matrices, RBF evaluations, feature maps, and permuted-statistic computation are all dense GEMM/elementwise — ideal for the GPU, and float32 halves the memory to fit VRAM in tiles.
- **value:** HIGH — both a large speedup (batched kernels/permutations) AND the memory relief that lets the scan run at national scale (tile the pairs across VRAM instead of a 48 GB CPU allocation).
- **plan:** route the live residual scan through a GPU HSIC (unifying with hsic.py per O9 — a modularization + GPU win together): feature maps + centered-kernel statistics + the permutation null as batched torch ops on tiles that fit `0.8·6.4 GB`; CPU fallback. Resolves O9 and the residual-scan memory ceiling simultaneously.

### G3 · `GPU-KRON` — MEDIUM — the Kronecker joint operator is native torch.einsum territory (once load-bearing)
- **detail:** `kron.py`'s 3-factor vec-trick matvec, factored solve, and CG are mode-wise tensor contractions — `torch.einsum` on GPU is the natural backend, and the national space factor (sparse S≈5570) + dense var/time factors would benefit. But currently `joint_logdet` is telemetry-only (not load-bearing), so the payoff waits on the operator driving something real (a joint marginal-likelihood, or a Kronecker-preconditioned solve used in the fit). Pairs with the math-ledger question of whether the separable operator should become the actual inference substrate.
- **value:** MEDIUM (HIGH if the joint operator becomes load-bearing).
- **plan:** a torch backend for `KroneckerPrecision.matvec/solve` (drop-in), enabled when the operator feeds a real computation; keep the numpy path as reference.

### G4 · `GPU-WHITEN` — MEDIUM — spatial-whitening sparse matvecs at national S
- **detail:** `whitened_lagged_correlation` accumulates `Ft @ (Q_sparse @ Ft.T)` over T time slices — sparse `(S×S)·(S×F)` matvecs at S≈5570. `torch.sparse` matmul on GPU could accelerate, but sparse-GPU overhead is real and the op is memory-bound; the win is uncertain and needs measurement. Precomputing the whitened features ONCE (A15) is the bigger lever and a prerequisite (don't accelerate a redundant computation).
- **value:** MEDIUM, measure first.
- **plan:** after A15 (compute whitening once), benchmark a torch.sparse whitening vs scipy; adopt only if it beats CPU including transfer.

### G5 · `GPU-POP-BLOCKED` — MEDIUM — re-open the population-tensor GPU path as batched locality blocks (honestly deferred, but the math now fits)
- **detail:** The population denominator solve was made CPU locality-blocked (POP-02 M3) and the GPU flag was removed (honestly, no wired path). But blocked solve = many small IDENTICAL per-block problems = a GPU batch, and the projected-gradient step (residual + non-negative projection) is exactly what `she/reconstruction/torch_kernels.py` already implements (orphaned). With M2 (float32 storage) landed and the blocked structure in place, a batched-block GPU solve is now a clean fit within 6 GB (each block ≪ VRAM).
- **value:** MEDIUM — throughput on the national denominator build.
- **plan:** wire `torch_kernels` behind the block loop with a VRAM preflight + CPU fallback (the G1 pattern from the compute plan); device telemetry so "was the GPU used" is answerable.

### G6 · `GPU-VRAM-SERIALIZE` — MEDIUM (prerequisite) — VRAM preflight has no reservation; concurrent CUDA admits can co-OOM 6 GB
- **detail:** `devices.py:resolve_torch_device` reads instantaneous free VRAM with no lock/reservation. With G1/G2/G5 introducing more CUDA tasks (some concurrent with the already-GPU HSIC/STDFM), two tasks can each pass preflight then collectively exceed 6 GB. A prerequisite for safely turning on more GPU paths.
- **value:** MEDIUM (enabler).
- **plan:** a process-wide CUDA admission semaphore / VRAM budget; re-check under lock; queue rather than co-admit.

### G-THEME — the reframed conclusion
The earlier "GPU gains are minor" was correct for the workload AS IT WAS (few, small ops). The current LDO is dominated by **repeated small dense ops** (stability/λ-path/holdout/exact-vs-approx refits) and **one huge dense scan** (HSIC residual, the 48 GB allocation). Those are precisely GPU-favorable, and float32 (already the declared dtype) makes them fit 6 GB in tiles. **G1 (batched stability ADMM) and G2 (GPU HSIC scan) are the two high-value, math-validity-neutral wins; both should be built.** They also compose with modularization (G2 unifies the two HSIC implementations, O9) and with the redundancy fixes (A15).

**`LDO-GPU-01` - HIGH - gpu_acceleration_candidate** - ADMM inner eigh (_prox_neg_logdet + _psd_project_shifted) is the dominant repeated small-dense op — move to torch.linalg.eigh on GPU
- detail: fit_sparse_plus_lowrank runs up to max_iter=500 ADMM iterations, each calling TWO dense symmetric eigendecompositions on the (q x q) working matrix (q = kept features ~= p*(K+1); national context p<=200, K<=1 => q up to ~400, national C25 disease-axis p~130). That is up to 1000 eigh per fit. A single run_ldo invokes fit_lagged_links ~19 times (1 base + 2 lambda-grid path-agreement + 2 exact-certify + 2 temporal-holdout + 12 stability subsamples), so ~19k dense eigh per national run. Each eigh is O(q^3): q=400 => ~6.4e7 flop, x19k => ~1.2e12 flop of eigendecomposition, plus the two @-products (vecs*d)@vecs.T of the same order. This is THE wall-clock hotspot and it is exactly the repeated-small-dense pattern GPUs win at. Redesign: replace np.linalg.eigh in _prox_neg_logdet/_psd_project_shifted with torch.linalg.eigh on a persistent CUDA tensor; keep S,L,U,R resident on-device for the whole loop so there is no per-iteration H2D/D2H copy (only the final readout leaves the GPU). A 400x400 eigh on an RTX 4050 is ~sub-millisecond and cuSOLVER batches the syevd well.
- expected_gain: Per-eigh GPU vs numpy LAPACK at q=400: ~10-30x on the decomposition; realistically 5-15x end-to-end on the ADMM loop once host-copy overhead is amortized by keeping iterates on-device. National run LDO wall-clock (the single largest cost) plausibly 5-10x.
- validity_preserved: PARTIAL RISK. The code deliberately does eigh in float64 (spectrum-reshaping corrupts small eigenvalues in f32 -> corrupts logdet). torch.linalg.eigh supports float64 on CUDA (cuSOLVER syevj/syevd f64), so run the GPU eigh in float64 to preserve the exact §V.1 policy — validity fully preserved, VRAM still tiny (400x400 f64 = 1.3MB). Do NOT drop to f32 for the eigh; only the bulk iterates may be f32.
- evidence: lowrank.py:55-81 (_prox_neg_logdet, _psd_project_shifted each do np.linalg.eigh in float64); lowrank.py:206-231 (loop runs both twice per iter, max_iter=500); orchestrator.py:195,214,233,246,250 + certgates.py:51 + holdout.py:70-71 show ~19 fit_lagged_links per run; edges.py:89 stability_select draws n_subsamples refits.
- recommendation: Add a torch-backed ADMM path in lowrank.py gated on resolve_torch_device('stdfm_solver' or a new 'ldo_admm' task) + q above a threshold (~128). Keep S,L,U,R,C as CUDA float64 tensors; use torch.linalg.eigh for both prox steps; only cast the final S,L to host for edge readout. Preserve the numpy path as the CPU fallback for small q and no-CUDA.

**`LDO-GPU-02` - HIGH - gpu_acceleration_candidate** - Batch the 12+ stability-subsample ADMM refits as one batched torch.linalg.eigh (b x q x q)
- detail: stability_select (edges.py) fits n_subsamples (default 12, orchestrator passes 12) INDEPENDENT ADMM solves on spatial/time subsamples — today parallelized only across CPU threads with BLAS pinned to 1 thread/worker (edges.py:108-121). These are structurally identical (q x q) problems differing only in the covariance C. torch.linalg.eigh accepts a batched (b, q, q) tensor and dispatches one batched cuSOLVER call. Because all subsamples share the same feature layout, the whole stability ensemble can run as a single (12, q, q) on-device ADMM: every prox step is one batched eigh, one batched matmul. The soft-threshold and PSD-clip are elementwise/broadcast. This collapses 12 sequential CPU eigensolve streams into one GPU kernel launch per iteration.
- expected_gain: GPU batched eigh over b=12, q~400 saturates the 4050 far better than 12 serialized 400^3 CPU solves. Expect 8-20x on the stability phase specifically, which is ~63% of the fit count (12 of 19). Also removes the threadpoolctl/BLAS-pinning complexity.
- validity_preserved: PRESERVED. Batched eigh in float64 is numerically identical per-slice to the serial eigh; the stability frequencies are unchanged. Only risk is that subsamples with different kept-feature sets have different q — handle by grouping by q or padding to max-q with identity blocks (padded rows are inert PSD). Deterministic index draws (edges.py:89) are preserved.
- evidence: edges.py:61-121 (stability_select: index_sets drawn up front, ThreadPoolExecutor over _subsample_edges, BLAS pinned to 1 thread); lowrank.py:64,79 (per-fit eigh); orchestrator.py:250-253 passes n_subsamples=12.
- recommendation: Add batched-ADMM entry point fit_sparse_plus_lowrank_batched(C_stack) that keeps a (b,q,q) tensor on CUDA and runs torch.linalg.eigh batched. Route stability_select through it when CUDA is present and q>128; fall back to the current thread-pool path otherwise. Pad ragged q per batch or bucket subsamples by q.

**`LDO-GPU-03` - HIGH - gpu_acceleration_candidate** - Residual-scan HSIC kernel cache + pairwise products are a huge dense scan — the 48GB hotspot — and are the strongest GPU/streaming candidate
- detail: scan_residual_nonlinear_edges builds, for EVERY variable, two doubly-centered n_eff x n_eff RBF kernels (exact mode, n_eff<=5000), retained in a cache: 2*p*n_eff^2*8 bytes = at p=130,n_eff=5000 ~= 48GB (envelope.py:74-95 states this explicitly and it is the single largest LDO allocation). Then p^2/2 pairs each do np.sum(kx*ky) plus 'permutations' null evals np.sum(kx*ky[ix_(pm,pm)]) — every null eval is an O(n^2) gather+multiply. This is a colossal dense-scan workload (p^2/2 * permutations * n^2 ~ for p=130,perm=200,n=5000 => ~2e14 elementwise ops). GPU-favorable AND the classic streaming/colossal-instantiation redesign: kernels need never be simultaneously materialized. Build each variable's centered kernel on the GPU on demand (or as a low-rank RFF/Nystrom feature map — already coded), stream pair statistics as batched tensor contractions (einsum 'ab,ab->' for exact, or feature cross-covariance fx.T@fy for approx). RFF/Nystrom features (n x n_features, n_features<=1024) are ~40MB/var, trivially VRAM-resident, and turn the null loop into a batched matmul.
- expected_gain: Memory: 48GB dense cache -> O(p*n*n_features) feature maps (~5GB f32 for p=130,n=5000,nf=512) or streamed exact kernels (never all held). Speed: null evals as batched GPU matmul over permutations = 20-50x vs the Python per-permutation np.sum loop; whole residual scan plausibly 10-30x. Critically, it moves the workload from 'refuses/coarsens for lack of 48GB RAM' to 'fits in 6GB VRAM as features'.
- validity_preserved: PRESERVED if the RFF/Nystrom path is used at national n (the code ALREADY switches to features for n>max_exact=5000; the 48GB case is the exact-mode boundary n_eff~5000). Statistical caveat: forcing the feature-map path slightly below 5000 to gain GPU/memory is an approximation of exact HSIC — but the module already sanctions it above 5000 and emits approximation diagnostics; lower the max_exact threshold under memory pressure with the existing warning. Exact GPU einsum in f64 is bit-comparable to numpy.
- evidence: residual_scan.py:94-183 (_centered_kernel n x n, _build_var_reprs retains per-var kernels, _pair_stat_and_null loops perms with np.ix_ gather); envelope.py:74-95 (documents 48GB at n_eff=5000,p=130); hsic.py:325-347 already has torch _rff_features/_nystrom_features/_feature_hsic on device.
- recommendation: Route the residual scan through the existing torch HSIC feature path (hsic.py _rff_features/_nystrom_features/_feature_hsic) on CUDA; batch the permutation nulls as fx.T @ fy[perm_stack] contractions. Lower effective max_exact when estimate_residual_scan_bytes exceeds a VRAM/RAM fraction rather than coarsening first.

**`LDO-DESIGN-06` - HIGH - foundational_design_flaw** - ~19 independent full ADMM refits per run recompute whitening+covariance from scratch — the problem shape should share the covariance and warm-start
- detail: Every fit_lagged_links call (base, 2x path-agreement, 2x exact-certify, 2x holdout, 12x stability) independently: (1) rebuilds the spatial precision, (2) recomputes the whitened/pairwise covariance over the (sub)sample, (3) cold-starts ADMM from S=I,L=0,U=0. The path-agreement and exact-certify refits differ ONLY in lambda1 or randomized-vs-exact readout — the covariance is IDENTICAL, yet it is recomputed each time. The lambda-path is the canonical warm-start case: solve at lambda, warm-start the next lambda from the previous S,L,U (ADMM converges in a handful of iterations instead of up to 500). This is a problem-shape flaw, not a local inefficiency: the orchestrator treats each refit as a black box instead of a continuation.
- expected_gain: Covariance reuse alone removes ~4 redundant whitening+covariance builds/run (path-agreement 2 + exact-certify 2 share the full-field covariance with the base fit). Warm-starting the lambda-path and exact-certify refits cuts their ADMM iteration counts ~3-10x. Combined, plausibly 30-50% off total run wall-clock before any GPU work, and it compounds with LDO-GPU-01/02.
- validity_preserved: PRESERVED. Warm-starting ADMM changes only the iterate trajectory, not the fixed point (converged S,L,U are identical to tol). Sharing an identical covariance across lambda-only refits is exact. Only the stability subsamples legitimately need fresh covariances (different data).
- evidence: orchestrator.py:195 (base), :214 (exact readout refit), :311-315 (path agreement), certgates.py:47-51 (per-lambda full fit_lagged_links), holdout.py:70-71,129 (exact/approx + train/test full fits); lowrank.py:200-203 cold-starts S=I,L=0,U=0 every call.
- recommendation: Factor fit_lagged_links into (a) build covariance and (b) ADMM-from-covariance-with-optional-warmstart. Compute the full-field covariance once, reuse it for base + path-agreement + exact-certify. Thread previous (S,L,U) into the lambda-grid and exact-vs-approx refits as warm starts.

**`LDO-SPEED-04` - MEDIUM - speed_hotspot** - whitened_lagged_correlation Gram accumulation is a Python-level T_eff x (K+1) loop of dense (F x S) matmuls — batch it
- detail: whitened_lagged_correlation (covariance.py:191-196) loops over t in [K,T) and inner lag in [0,K], each iteration assembling Ft (F x S) and doing G += Ft @ (Q_sparse @ Ft.T). At national S~5570, F=p*(K+1)~400, this is T_eff*(K+1) Python iterations each doing a dense (F x S)@(S x F)=~F^2*S ~ 400^2*5570 ~ 9e11 flop-ish accumulated, all single-threaded numpy with a Python loop overhead per time slice. Q_sparse@Ft.T is a sparse-times-dense (scipy) that does not use the GPU. This whitening is computed once per fit but the fit runs ~19x/run, and it is the dominant non-eigh cost of the covariance stage. It is a textbook batched-GEMM + sparse-matmul that torch.sparse.mm on CUDA does well; the whole time loop can be a single batched einsum if the lag blocks are formed by strided views.
- expected_gain: Batching the GEMM/SpMM on GPU (torch.sparse.mm + bmm) 5-15x on the whitening stage; even a pure-numpy fix (accumulate all Ft into one (F, S*T_eff) and do one Q-SpMM + one GEMM) removes the Python-loop overhead for a 2-4x CPU win.
- validity_preserved: PRESERVED. Pure re-association of the same sums (the Gram is a linear accumulation); float32 on GPU risks small error in the correlation but the result is projected to nearest-correlation anyway (_nearest_correlation) and downstream thresholds are coarse (edge_threshold 0.05). Keep f64 for the diagonal/normalization to be safe.
- evidence: covariance.py:188-203 (per-t, per-lag Python loop building Ft and accumulating G, R); precision.py:87-98 dense _whiten_spatial also loops per variable.
- recommendation: Move Q_sparse to a torch sparse CUDA tensor once; form the lag-extended feature stack via strided views; accumulate G with torch.sparse.mm + batched matmul. Fall back to a single-shot numpy accumulation (one big GEMM) when no CUDA.

**`LDO-MEM-05` - MEDIUM - memory_hotspot** - pairwise_correlation materializes five dense (q x q) BLAS products simultaneously — the fit-path RAM peak
- detail: pairwise_correlation (covariance.py:83-96) forms n_ab, Sx, Sxx, Cxy (each q x q f64) plus X, M, X0 (each q x n f64). At the lag-extended scale q=p*(K+1) and n=S*T_eff, X/M/X0 are the big ones: q=400, n=5570*24~1.3e5 => each q x n f64 ~ 400*1.3e5*8 ~ 0.4GB, three of them ~1.3GB, held together with four q x q. This is the fit path's RAM peak (envelope.py models it as 'samples' + 'cov' terms). It fits 34GB RAM but is redundant: M is boolean-castable, X0 duplicates X. On VRAM (6.4GB) the q x n blocks would be the binding constraint if the whole fit moved to GPU.
- expected_gain: Memory: cast M to float32/bool-view and reuse X0's buffer -> ~2-3x reduction of the qxn working set (from ~1.3GB to ~0.5GB); enables the covariance stage to fit VRAM alongside the ADMM. Minor speed win from smaller BLAS operands (better cache).
- validity_preserved: PRESERVED for the boolean-mask and buffer-reuse; the moment algebra is unchanged. float32 on the qxn products is a mild precision risk in var/cov but the ratio cancels 1/n and the output is re-projected to nearest-correlation; keep the final normalization in f64.
- evidence: covariance.py:79-96 (X, M, X0 all q x n f64; n_ab,Sx,Sxx,Cxy all q x q); envelope.py:52-71 charges the samples matrix S*(T-K)*pk as the bulk term.
- recommendation: Represent M as float32 (or compute n_ab via a boolean matmul), overwrite X0 in place from X, and free X once X0/M are formed. When routing the fit to GPU, chunk the qxn products over time-blocks so only a slab of n is resident.

**`LDO-NUM-07` - MEDIUM - numerical_method_swap** - L-step full eigh only needs the top-r PSD spectrum — swap the dense _psd_project_shifted eigh for a randomized/truncated eigensolve
- detail: _psd_project_shifted (lowrank.py:69-81) does a full O(q^3) eigh every iteration to clip eigenvalues at (val-shift)>0, but L is low-rank by construction (few shared drivers; factor_rank_cap=24). After a few iterations only the top ~r eigenvalues exceed the shift; the rest clip to zero and contribute nothing. A truncated/randomized symmetric eigensolver (torch.lobpcg, or randomized_svd already imported for the readout) computing the top-(r+buffer) eigenpairs is O(q^2 * r) vs O(q^3) — for q=400, r~30 that is ~13x fewer flop on the single most-repeated op after the logdet prox. The logdet prox (_prox_neg_logdet) genuinely needs the full spectrum (all eigenvalues enter d), so it stays full; but the PSD projection does not.
- expected_gain: ~5-13x on the L-step specifically (one of the two per-iteration eighs), i.e. up to ~2x on the whole ADMM inner loop when combined with keeping the logdet prox full. Stacks multiplicatively with the GPU move.
- validity_preserved: PARTIAL RISK. Truncation is exact only if the true numerical rank of (S-R-U) at the shift is <= the computed r+buffer. Near convergence L is genuinely low-rank so this holds; early iterations may have more mass above the shift. Mitigate by computing r_eff adaptively (grow until the smallest kept eigenvalue < shift) so the projection is provably exact, or verify residual. Keep a full-eigh fallback when the rank estimate saturates.
- evidence: lowrank.py:69-81 (_psd_project_shifted full eigh + clip), :222 (called every iter), :84-109 (_low_rank_factors already uses randomized_svd for the SAME L at readout, proving low-rank-ness); factor_rank_cap=24 default (lowrank.py:125).
- recommendation: Replace the L-step eigh with an adaptive truncated symmetric eigensolver (torch.lobpcg on GPU or scipy randomized) targeting rank r that grows until the smallest kept eigenvalue falls below the shift, guaranteeing an exact PSD projection. Leave _prox_neg_logdet as a full eigh (needs all eigenvalues).

- evidence: config/compute.yaml cuda.enabled_for (pirs_hsic_*, race_bridge_*, stdfm_solver only; explicit note that population kernels were REMOVED for being orphaned); devices.py:75 (use_cuda gated on task_id in enabled_for); lowrank.py/covariance.py/lags.py import only numpy/scipy, never torch.

**`LDO-SPEED-08` - LOW - speed_hotspot** - O(q^2) Python triple-loops for latent_shared pair enumeration and direct-edge readout
- detail: After ADMM, direct_edges is built by a Python double loop over i<j (lowrank.py:242-246), and latent_shared by a triple loop over factors x strong-var-pairs (lowrank.py:274-282) plus a dict-dedup and a sort. At national q~400 the i<j loop is ~80k Python iterations of float() + abs() per fit, x19 fits/run. The lags.py readout was already vectorized (lags.py:153-193 uses np.ix_/argmax), but lowrank.py's own readout remains a Python loop.
